    <question>
        <title>Чем ConcurrentHashMap отличается от synchronized Map?</title>
        <groups>
            <group>HashMap</group>
        </groups>
        <short><b>ConcurrentHashMap</b> использует <b>сегментированную блокировку</b> (или блокировку отдельных корзин в Java 8+), что позволяет нескольким потокам одновременно читать и записывать в разные части карты. <b>Collections.synchronizedMap</b> блокирует всю карту при любом обращении, что приводит к последовательному доступу и снижению производительности в многопоточной среде. <code>ConcurrentHashMap</code> также поддерживает <code>null</code> и итераторы с <code>weak consistency</code>.</short>
        <long>
            <b>Различия:</b>
            <ul>
                <li><b><code>ConcurrentHashMap</code>:</b>
                    <ul>
                        <li>Разработан для высокой производительности в многопоточной среде.</li>
                        <li>В Java 8+ использует блокировку только на уровне отдельных корзин (buckets).</li>
                        <li>Операции чтения (<code>get</code>) не блокируются, запись блокирует только конкретную корзину.</li>
                        <li>Итераторы не бросают <code>ConcurrentModificationException</code>.</li>
                        <li>Не поддерживает <code>null</code> ключи или значения.</li>
                    </ul>
                </li>
                <li><b><code>Collections.synchronizedMap()</code>:</b>
                    <ul>
                        <li>Синхронизирует все методы с помощью <code>synchronized</code> на самом объекте.</li>
                        <li>Блокирует всю карту при любом доступе (чтение и запись).</li>
                        <li>Может использовать итераторы только с внешней синхронизацией.</li>
                        <li>Поддерживает <code>null</code>.</li>
                    </ul>
                </li>
            </ul>
        </long>
    </question>

    <question>
        <title>Как работает ExecuteService, если его вызвать внутри транзакции?</title>
        <groups>
            <group>Транзакции</group>
        </groups>
        <short>Если <code>ExecutorService</code> вызывается внутри транзакции, задачи, выполняемые в отдельных потоках, <b>не наследуют</b> контекст транзакции (транзакция не распространяется на новые потоки). Это может привести к <b>несогласованности данных</b>: основная транзакция может быть откачена, а асинхронная задача уже выполнила изменения. Решение: использовать синхронное выполнение или передавать необходимые данные отдельно.</short>
        <long>
            <b>Особенности работы ExecutorService в транзакции:</b>
            <ul>
                <li>Транзакция привязана к текущему потоку (<code>ThreadLocal</code>).</li>
                <li>Асинхронные задачи в пуле потоков не видят текущую транзакцию.</li>
                <li>Если основная транзакция откатывается, а асинхронная задача уже выполнила <code>INSERT</code>/<code>UPDATE</code>, данные останутся в БД.</li>
                <li><b>Рекомендации:</b>
                    <ul>
                        <li>Избегать асинхронных операций внутри транзакций.</li>
                        <li>Если необходимо, передавать нужные данные (ID, DTO) отдельно.</li>
                        <li>Использовать <code>@Transactional</code> в самом асинхронном методе (транзакция будет новая).</li>
                    </ul>
                </li>
            </ul>
        </long>
    </question>

    <question>
        <title>Что произойдет если внутри транзакции возникнет Exception или RuntimeException?</title>
        <groups>
            <group>Транзакции</group>
        </groups>
        <short>По умолчанию Spring откатывает транзакцию, если возникает <b>RuntimeException</b> (или его наследник). <b>Checked Exception</b> (<code>Exception</code>) не приводит к откату, если не указано явно (<code>@Transactional(rollbackFor = Exception.class)</code>). Транзакция будет закоммичена, если перехватить исключение и не пробросить его дальше.</short>
        <long>
            <b>Поведение Spring @Transactional:</b>
            <ul>
                <li><b><code>RuntimeException</code></b> (unchecked):<br/>
                    Откат транзакции (<code>rollback</code>).<br/>
                    <i>Пример:</i> <code>NullPointerException</code>, <code>IllegalArgumentException</code>.</li>
                <li><b><code>Exception</code></b> (checked):<br/>
                    <b>Нет</b> отката (<code>commit</code>), если не указано <code>rollbackFor</code>.<br/>
                    <i>Пример:</i> <code>IOException</code>, <code>SQLException</code>.</li>
                <li><b>Обработка исключения внутри метода:</b><br/>
                    Если исключение поймано и не проброшено дальше, транзакция будет закоммичена (если не вызван <code>setRollbackOnly()</code>).</li>
                <li><b>Параметры:</b>
                    <ul>
                        <li><code>@Transactional(rollbackFor = Exception.class)</code> — откат для всех исключений.</li>
                        <li><code>@Transactional(noRollbackFor = RuntimeException.class)</code> — не откатывать для конкретного исключения.</li>
                    </ul>
                </li>
            </ul>
        </long>
    </question>

        <title>Что произойдет при уровнях изоляции repeateableRead и sinchronized если 2 транзакции попытаются изменить одну строку в базе</title>
        <groups>
            <group>изоляция</group>
        </groups>
        <short>При <b>REPEATABLE READ</b> и использовании <b>синхронизации</b> (например, пессимистичной блокировки <code>SELECT ... FOR UPDATE</code>) вторая транзакция <b>заблокируется</b> и будет ждать, пока первая не завершится. В PostgreSQL уровень <code>REPEATABLE READ</code> предотвращает <b>неповторяемое чтение</b>, но не конфликты при обновлении одной строки (если нет явной блокировки). Без явной блокировки вторая транзакция может перезаписать изменения первой (lost update).</short>
        <long>
            <b>Сценарий:</b>
            <ul>
                <li>Транзакция 1 читает строку (значение 10).</li>
                <li>Транзакция 2 читает ту же строку (значение 10).</li>
                <li>Транзакция 1 обновляет строку до 20 и коммитит.</li>
                <li>Транзакция 2 обновляет строку на основе старого значения (10) до 15 и коммитит.</li>
                <li><b>Результат:</b> Значение в строке 15, а не 20 (потеря обновления).</li>
            </ul>
            <b>Как избежать:</b>
            <ul>
                <li>Использовать <b>пессимистичную блокировку</b>: <code>SELECT ... FOR UPDATE</code>.</li>
                <li>Использовать <b>оптимистичную блокировку</b> (версия).</li>
                <li>Уровень <code>SERIALIZABLE</code> предотвращает все аномалии, но может вызывать ошибки сериализации.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Как работают оптимистиченые блокировки? Кто именно ставит версию, это происходит внутри транзакции или нет?</title>
        <groups>
            <group>изоляция</group>
        </groups>
        <short>Оптимистичная блокировка работает через <b>версионирование</b> (<code>@Version</code> в JPA). Версия обновляется <b>внутри транзакции</b> при обновлении сущности. При сохранении Hibernate проверяет, что версия в БД совпадает с версией сущности. Если нет — выбрасывается <code>OptimisticLockException</code>. Версия не обновляется при чтении, только при записи.</short>
        <long>
            <b>Как работает @Version:</b>
            <ul>
                <li><b>Поле версии:</b> <code>@Version private Long version;</code></li>
                <li><b>При загрузке:</b> Hibernate загружает текущую версию из БД.</li>
                <li><b>При обновлении:</b> Hibernate выполняет <code>UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?</code>.</li>
                <li><b>Если версия не совпала:</b> Обновление не затрагивает строки, Hibernate выбрасывает <code>OptimisticLockException</code>.</li>
                <li><b>Поле версии обновляется внутри транзакции</b> (в момент выполнения <code>UPDATE</code>).</li>
                <li><b>Кто ставит версию:</b> Hibernate автоматически инкрементирует версию при сохранении.</li>
            </ul>
            <b>Когда использовать:</b>
            <ul>
                <li>При редких конфликтах (например, редактирование профиля).</li>
                <li>В системах, где важна производительность, а не блокировки.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Что такое happens-before? Как работает и что гарантирует?</title>
        <groups>
            <group>потоки</group>
        </groups>
        <short><b>Happens-before</b> — это отношение порядка в Java Memory Model, которое гарантирует <b>видимость</b> изменений между потоками. Если операция A happens-before операция B, то все изменения, сделанные в A, видны в B. Это работает через <b>синхронизацию</b> (<code>synchronized</code>, <code>volatile</code>, <code>Lock</code>). Гарантирует, что изменения не будут переупорядочены компилятором или процессором.</short>
        <long>
            <b>Гарантии happens-before:</b>
            <ul>
                <li>Запись в <code>volatile</code> переменную happens-before последующее чтение этой переменной.</li>
                <li>Выход из <code>synchronized</code> блока happens-before вход в <code>synchronized</code> блок.</li>
                <li>Запуск потока (<code>Thread.start</code>) happens-before первое действие в этом потоке.</li>
                <li>Завершение потока (<code>Thread.join</code>) happens-before возврат из <code>join()</code>.</li>
            </ul>
            <b>Что гарантирует:</b>
            <ul>
                <li>Все изменения, сделанные до операции A, видны в операции B.</li>
                <li>Предотвращает переупорядочивание инструкций.</li>
                <li>Обеспечивает консистентность данных между потоками.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Почему при старте Keycloak-пода в K8s могут быть длинные GC-паузы?</title>
        <groups>
            <group>Авторизация</group>
        </groups>
        <short>При старте Keycloak происходит <b>активная инициализация</b> кэшей, загрузка провайдеров и метаданных, что создаёт большое количество объектов. Это может вызвать <b>длительные GC-паузы</b>, особенно при использовании старого сборщика (Parallel GC). Рекомендуется использовать <b>G1 GC</b> с настройками <code>-XX:MaxGCPauseMillis</code> и предварительным "прогревом" приложения.</short>
        <long>
            <b>Причины длительных GC-пауз:</b>
            <ul>
                <li>Интенсивное создание объектов во время инициализации (загрузка провайдеров, кэшей).</li>
                <li>Использование старого сборщика (<code>Parallel GC</code>).</li>
                <li>Недостаточный размер кучи (<code>-Xmx</code>).</li>
                <li>Отсутствие прогрева JVM перед приёмом трафика.</li>
            </ul>
            <b>Решения:</b>
            <ul>
                <li>Использовать <b>G1 GC</b>: <code>-XX:+UseG1GC -XX:MaxGCPauseMillis=200</code>.</li>
                <li>Увеличить память: <code>-Xmx2g</code> (в зависимости от нагрузки).</li>
                <li>Включить <code>-XX:+ParallelRefProcEnabled</code> для ускорения обработки ссылок.</li>
                <li>Использовать прогревающие запросы (warm-up) перед включением в трафик.</li>
                <li>Настроить <code>readinessProbe</code> на ожидание полной инициализации.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Как запустить JFR-запись на production-сервисе без перезапуска? Какие события анализируете в первую очередь при деградации latency?</title>
        <groups>
            <group>JFR</group>
        </groups>
        <short><b>JFR (Java Flight Recorder)</b> можно запустить на работающем приложении с помощью <code>jcmd</code> (без перезапуска): <code>jcmd &lt;pid&gt; JFR.start name=myrecording settings=profile duration=60s filename=myrecording.jfr</code>. При деградации latency в первую очередь анализируют: <b>GC паузы</b> (<code>GC Pauses</code>), <b>блокировки</b> (<code>Java Monitor Wait</code>, <code>Thread Park</code>), <b>сетевые задержки</b> (<code>Socket Read</code>, <code>Socket Write</code>) и <b>системные вызовы</b> (<code>File I/O</code>, <code>CPU Load</code>).</short>
        <long>
            <b>Запуск JFR:</b>
            <ul>
                <li><b>Найти PID:</b> <code>jps</code> или <code>ps -ef | grep java</code>.</li>
                <li><b>Запустить запись:</b> <code>jcmd &lt;pid&gt; JFR.start name=myrecording settings=profile duration=60s filename=myrecording.jfr</code>.</li>
                <li><b>Остановить запись:</b> <code>jcmd &lt;pid&gt; JFR.stop name=myrecording</code>.</li>
                <li><b>Параметры:</b>
                    <ul>
                        <li><code>settings=profile</code> — профильная запись с детальными событиями.</li>
                        <li><code>duration=60s</code> — длительность записи.</li>
                        <li><code>filename</code> — путь к файлу (можно указать <code>/tmp</code>).</li>
                    </ul>
                </li>
            </ul>
            <b>При деградации latency:</b>
            <ul>
                <li><b>GC Pauses:</b> Длительные паузы сборщика мусора.</li>
                <li><b>Java Monitor Wait:</b> Блокировки на мониторах (<code>synchronized</code>).</li>
                <li><b>Thread Park:</b> Ожидание потоков (<code>LockSupport.park()</code>).</li>
                <li><b>Socket Read/Write:</b> Сетевые задержки.</li>
                <li><b>CPU Load:</b> Высокая загрузка процессора.</li>
                <li><b>File I/O:</b> Медленные операции ввода-вывода.</li>
            </ul>
        </long>
    </question>

        <title>Как снять HeapDump с Java-процесса в контейнере? Как найти memory leak через Eclipse MAT (dominator tree, histogram)?</title>
        <groups>
            <group>JFR</group>
        </groups>
        <short><b>Heap Dump</b> снимается через <code>jcmd</code> или <code>jmap</code>: <code>jcmd &lt;pid&gt; GC.heap_dump /path/to/dump.hprof</code>. <b>Eclipse MAT</b> использует <b>Histogram</b> (сортировка по количеству объектов) и <b>Dominator Tree</b> (поиск крупных объектов). Поиск утечки: найти объекты, которые не должны существовать (например, статические коллекции, удерживающие большие объекты), проанализировать <b>GC Roots</b>.</short>
        <long>
            <b>Снятие Heap Dump:</b>
            <ul>
                <li><b>Через jcmd:</b> <code>jcmd &lt;pid&gt; GC.heap_dump /tmp/dump.hprof</code>.</li>
                <li><b>Через jmap:</b> <code>jmap -dump:live,format=b,file=/tmp/dump.hprof &lt;pid&gt;</code>.</li>
                <li><b>В Kubernetes:</b> <code>kubectl exec -it &lt;pod&gt; -- jcmd 1 GC.heap_dump /tmp/dump.hprof</code>.</li>
                <li><b>Важно:</b> Убедиться, что есть место на диске (heap может быть большим).</li>
            </ul>
            <b>Анализ в Eclipse MAT:</b>
            <ul>
                <li><b>Histogram:</b> Сортировка по количеству объектов. Искать классы с подозрительно большим количеством.</li>
                <li><b>Dominator Tree:</b> Показывает объекты, которые удерживают память. Искать большие объекты с сильными ссылками.</li>
                <li><b>Leak Suspects:</b> Автоматический отчёт о потенциальных утечках.</li>
                <li><b>GC Roots:</b> Найти корневые ссылки, удерживающие объекты.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Как снять thread dump? Как по дампу определить deadlock? Что означает состояние BLOCKED vs WAITING?</title>
        <groups>
            <group>JFR</group>
        </groups>
        <short><b>Thread Dump</b> снимается через <code>jcmd</code> или <code>kill -3</code>: <code>jcmd &lt;pid&gt; Thread.print</code>. <b>Deadlock</b> определяется по наличию циклических зависимостей между блокировками (<code>BLOCKED</code> состояния). <b>BLOCKED</b> — ожидание монитора (<code>synchronized</code>). <b>WAITING</b> — ожидание уведомления (<code>wait()</code>, <code>LockSupport.park()</code>).</short>
        <long>
            <b>Снятие Thread Dump:</b>
            <ul>
                <li><b>jcmd:</b> <code>jcmd &lt;pid&gt; Thread.print</code>.</li>
                <li><b>jstack:</b> <code>jstack &lt;pid&gt;</code>.</li>
                <li><b>kill -3:</b> <code>kill -3 &lt;pid&gt;</code> (записывает в stdout).</li>
                <li><b>В Kubernetes:</b> <code>kubectl exec -it &lt;pod&gt; -- jcmd 1 Thread.print</code>.</li>
            </ul>
            <b>Поиск deadlock:</b>
            <ul>
                <li>Искать потоки с состоянием <code>BLOCKED</code>, которые ждут один другой.</li>
                <li>Искать циклические зависимости в <code>waiting to lock</code> и <code>locked</code>.</li>
                <li>Использовать анализаторы (JStack, VisualVM) для выявления deadlock.</li>
            </ul>
            <b>Состояния:</b>
            <ul>
                <li><b><code>BLOCKED</code>:</b> Ожидает захвата монитора (<code>synchronized</code>).</li>
                <li><b><code>WAITING</code>:</b> Ожидает уведомления (<code>Object.wait()</code> без таймаута, <code>LockSupport.park()</code>).</li>
                <li><b><code>TIMED_WAITING</code>:</b> Ожидание с таймаутом (<code>Thread.sleep()</code>, <code>Object.wait(timeout)</code>).</li>
                <li><b><code>RUNNABLE</code>:</b> Выполняется или готов к выполнению.</li>
            </ul>
        </long>
    </question>

    <question>
        <title>Как включить GC-логи в контейнере? На какие метрики смотрите при анализе: pause time, throughput, allocation rate?</title>
        <groups>
            <group>JFR</group>
        </groups>
        <short><b>GC-логи</b> включаются параметрами JVM: <code>-Xlog:gc*</code> (Java 9+) или <code>-XX:+PrintGCDetails</code> (Java 8). При анализе смотрят: <b>Pause Time</b> (время пауз GC), <b>Throughput</b> (процент времени приложения), <b>Allocation Rate</b> (скорость выделения памяти). Высокий Allocation Rate может указывать на создание большого количества объектов, что требует оптимизации.</short>
        <long>
            <b>Включение GC-логов:</b>
            <ul>
                <li><b>Java 8:</b> <code>-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/to/gc.log</code>.</li>
                <li><b>Java 9+:</b> <code>-Xlog:gc*:file=/path/to/gc.log:time,uptime</code>.</li>
                <li><b>В Kubernetes:</b> Добавить параметры в <code>JAVA_OPTS</code>.</li>
            </ul>
            <b>Метрики для анализа:</b>
            <ul>
                <li><b>Pause Time:</b> Среднее и максимальное время пауз (<code>GC pause</code>).</li>
                <li><b>Throughput:</b> Процент времени, когда приложение работало (<code>1 - pause_time / total_time</code>).</li>
                <li><b>Allocation Rate:</b> Скорость выделения памяти (<code>allocated / time</code>).</li>
                <li><b>Heap Size:</b> Размер кучи до и после GC.</li>
                <li><b>GC Frequency:</b> Частота сборок (Minor/Major).</li>
            </ul>
            <b>Инструменты:</b>
            <ul>
                <li><b>GCViewer:</b> Визуализация GC-логов.</li>
                <li><b>Prometheus + Grafana:</b> Мониторинг метрик.</li>
            </ul>
        </long>
    </question>

        <title>Жизненный цикл Maven-сборки: что происходит на фазе package? Чем install отличается от deploy?</title>
        <groups>

        </groups>
        <short><b>Bulkhead</b> изолирует ресурсы (пулы потоков, соединения) между зависимостями, чтобы сбой в одной зависимости не влиял на другие.             </ul>
            <b>Пример:</b>
            <ul>
                <li>Сервис A вызывает сервис B и сервис C.</li>
                <li>У каждого свой пул (10 потоков).</li>
                <li>Если B падает, пул B заполняется, но C продолжает работать.</li>
            </ul>
            <b>Реализация:</b>
            <ul>
                <li>Resilience4j: <code>@Bulkhead(name = "serviceB", type = Bulkhead.Type.THREADPOOL)</code>.</li>
            </ul>
        </long>
    </question>

        <title>Как настроить readiness probe для Java-приложения в K8s? Почему liveness probe не должна проверять внешние зависимости?</title>
        <groups>
            <group>Kubernetes</group>
        </groups>
        <short><b>Readiness probe</b> проверяет, готов ли под принимать трафик. Настраивается через <code>httpGet</code> на эндпоинт <code>/actuator/health/readiness</code>. <b>Liveness probe</b> проверяет, жив ли под. Она <b>не должна проверять внешние зависимости</b> (БД, API), потому что при их недоступности K8s будет перезапускать под, что может привести к каскадным сбоям. Liveness должна проверять только внутреннее состояние JVM.</short>
        <long>
            <b>Readiness probe:</b>
            <ul>
                <li><code>httpGet: { path: /actuator/health/readiness, port: 8080 }</code></li>
                <li>Если возвращает 200, под готов принимать трафик.</li>
                <li>Используется для отключения трафика во время старта.</li>
            </ul>
            <b>Liveness probe:</b>
            <ul>
                <li><code>httpGet: { path: /actuator/health/liveness, port: 8080 }</code></li>
                <li>Проверяет только JVM (UP/DOWN).</li>
                <li>Не должна проверять БД, внешние API.</li>
                <li>Если проверка падает, под перезапускается.</li>
            </ul>
            <b>Настройка Spring Boot:</b>
            <ul>
                <li><code>management.endpoint.health.probes.enabled=true</code></li>
                <li><code>management.endpoint.health.group.readiness.include=db,ping</code></li>
            </ul>
        </long>
